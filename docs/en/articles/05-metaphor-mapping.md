# Dream Metaphor Mapping: Compile, Run, Debug, Commit, Deploy

Dream coding uses a set of metaphors to describe each stage of traditional development. These metaphors are not mere rhetoric: they give each stage a particular meaning, and they determine how the developer should act at that stage. Below, the five main stages are matched one by one.

Compiling corresponds to "compiling in the subconscious." A traditional compiler reads source code, checks the syntax, and generates machine code. In dream coding, compilation is done by the brain during sleep. It does not necessarily follow the syntax strictly; instead, it organizes daytime impressions into a structure that can run. As a result, the product of compilation is often more complete than the source code, but also vaguer, and it sometimes adds parts that were never written down.

Running corresponds to "running in non-existence." The program executes in the dream, but the dream has no real hardware and no real input or output. This makes running boundless: memory seems infinite, network requests always succeed, and asynchronous callbacks all finish before waking. Of course, these are metaphors. In this project's implementation, `dc run` does execute the script for real; only when the script fails does its output end with a segfault.

Debugging corresponds to "dream interpretation." Traditional debugging finds the cause of an error and fixes it; dream coding asks the developer to understand the symbolic meaning of the error. For example, a null pointer exception might mean you could not find something in the dream, and a stack overflow might mean you kept walking the same staircase in the dream. This interpretation is not guaranteed to be accurate, but it forces the developer to think about the problem from a higher level.

Committing corresponds to "commit upon falling asleep." A traditional commit is an active action: the developer decides when to save progress. Dream coding places the commit at the moment of falling asleep, which means the developer, at the moment of leaving work, hands the day's results to the subconscious. If you still remember the dream after waking, you can make a real commit then.

Deploying corresponds to "wake up and pretend nothing happened." Deployment hands code to real users; dream coding asks the developer to stay calm after waking and not rush to bring the dream's results into reality. This metaphor emphasizes a sense of boundaries: the results of the dream belong to the dream, and real-world results need to be verified separately.

These five metaphors form a closed loop. Propose ideas during the day, compile and run at night, interpret after waking, and then decide whether to commit and deploy. Each stage has clear boundaries and clear actions.

Understanding this mapping helps communication within a team. When someone says "I'm going to compile in my dream tonight," others understand that he has handed the compilation work to sleep and will check the results after waking. The metaphor thus becomes a shared language that keeps the whole team's work rhythm consistent.
