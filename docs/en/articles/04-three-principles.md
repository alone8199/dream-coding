# The Three Principles of Dream Coding

The dream coding process looks casual, but behind it lie three explicit principles. These principles are written in `CONTRIBUTING.md`, and they are conventions that every participant should follow. Understanding them matters more than memorizing the command for each step.

The first principle: do not debug.

Debugging is the action daytime developers know best: see an error, locate the cause, change the code, and run it again. Dream coding asks you to give up this action. When you wake to find `Segmentation fault (dream dumped)`, the right response is to accept it and then interpret what it means, rather than immediately opening the editor to patch it. The purpose of this principle is to keep developers from treating sleep as an extended daytime, which would cost dreams their independent value.

The second principle: do not force a commit.

Committing code is a deterministic action: it fixes a state so that others can review and use it. Dream coding holds that this kind of certainty is premature before sleep. It is only appropriate to commit when you fall asleep, or when you still remember the dream's content after waking. Forcing a commit of code written during the day and unverified in a dream would fill the repository with unreliable history.

The third principle: do not deploy.

Deployment means handing code over to a real environment. Dream coding asks you to pretend nothing happened after waking, that is, not to carry the results of the dream into reality. This principle does not ask people to turn a blind eye to the results. It is a reminder that running in a dream and running for real are two different things. A test that passes in a dream does not mean it will pass in reality.

These three principles share one thing: they all restrain the developer's impulses. Daytime developers are used to acting immediately, while dream coding asks them to hold back. This restraint is not for the sake of laziness; it is to leave room for thought.

In real team collaboration, these principles also help draw boundaries. When a PR was written in a dream, reviewers should recognize its uncertainty and reconfirm it in a second round of review after waking. This respects the value of the dream without giving up quality control.

Following the principles is not easy. Many developers cannot help modifying code after waking, or hastily committing before sleep. But every violation turns dream coding back into an ordinary development method. Sticking to these three principles is what truly distinguishes this technique from other development approaches.
