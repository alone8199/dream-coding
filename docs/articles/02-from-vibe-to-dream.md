# 02 从 vibe coding 到 dream coding

[中文](./02-from-vibe-to-dream.md) | [English](./02-from-vibe-to-dream.en.md)

要理解梦境编程的位置，可以先看它的前辈。近几年最流行的开发方式之一是 vibe coding：开发者不再逐行思考代码，而是描述大致的感觉，让 AI 生成实现，然后通过运行结果判断方向是否对。vibe coding 的效率很高，但它的产出常常是能跑却难以维护的代码，人们把这类结果戏称为"屎山"。

vibe coding 把注意力放在了生成速度上。开发者的主要动作是提出感觉、等待输出、再提出新的感觉。这个循环很快，但每一轮都需要人在场，人的注意力始终处于活跃状态。这恰恰是问题所在：活跃的注意力会不断打断推演，让人在细节里迷失方向。

梦境编程沿着同样的方向，又往前走了一步。它问的是：如果开发者根本不在场，结果会怎样？答案是，代码会在睡眠中被"运行"，产出一个不能直接使用的版本。这个版本的价值不在于它能跑，而在于它揭示了开发者在白天没有想清楚的部分。

两种方式的差异可以归纳为几个维度。在动作上，vibe coding 需要持续的输入，梦境编程只需要一次输入。在产出上，vibe coding 产出可运行的代码，梦境编程产出可以用来反思的结果。在调试上，vibe coding 依赖错误信息和 AI 的修补，梦境编程则要求开发者去理解醒来后的残留印象。在归宿上，前者的尽头常常是 Stack Overflow，后者的尽头则是对梦境的解读。

这种对比并不意味着梦境编程比 vibe coding 更好。两者解决的是不同的问题。当你需要快速验证一个想法时，vibe coding 更合适；当你需要让想法沉淀，并且愿意接受一段时间的等待时，梦境编程更合适。

从工程角度看，梦境编程也有一个值得借鉴的思路：把"生成"和"验证"之间的时间拉长。很多时候，我们之所以写出糟糕的代码，是因为生成和验证挤在同一个时间段里，没有留下思考的空间。睡眠提供了这样的空间。

因此，梦境编程可以看作是对 vibe coding 的一种补充，而不是替代。它提醒我们，开发的速度并不总是越快越好。有些结论需要时间才能成形，而睡眠恰好是最安静、最不受打扰的那段时间。
