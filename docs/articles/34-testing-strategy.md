# 34 测试策略：单元测试与端到端测试

[中文](./34-testing-strategy.md) | [English](./34-testing-strategy.en.md)

测试是保证 `dc` 行为正确的基础。由于梦境编程的核心在睡眠中完成，测试在这里承担了一个特殊的角色：它是白天唯一可以确定地验证行为的手段。因此，`dc` 的测试策略分为几个层次，每一层都针对不同的风险。

最底层是运行器的单元测试，位于 `runtime/tests/runner_test.cpp`。它测试命令行的行为：`help` 和 `version` 是否输出正确的内容，`sleep` 的时长检查是否生效，`wake` 是否输出段错误，文件不存在和后缀错误是否返回正确的退出码，未知命令是否被拒绝。这些测试不关心脚本的执行，只关心命令本身的契约。

第二层是解释器的测试，位于 `runtime/tests/interp_test.cpp`。它直接创建解释器，执行一段段代码，然后检查输出和错误。测试覆盖了算术、字符串、变量作用域、控制流、函数、闭包、列表、字典、逻辑短路、错误行号、语法错误、递归限制、内置函数、标准库、原生扩展和文件模块。每一项测试都是一个小的脚本片段，失败时会打印期望值和实际值，方便定位问题。

文件模块的测试比较特殊。它会在系统的临时目录中创建模块文件，然后通过 `run_file` 执行入口文件，检查导入是否正确。测试结束后会清理这些文件。这种做法让测试既覆盖了真实的文件操作，又不会在仓库中留下垃圾。

第三层是端到端的冒烟测试，位于持续集成的配置中。它不直接调用内部接口，而是通过命令行运行安装后的 `dc`。它检查版本输出、入口梦境的执行、示例脚本的语法和输出，以及运行时错误的退出码。这一层的价值在于，它验证了整个程序在真实环境中的表现，而不仅仅是各个模块的正确性。

测试的设计有一个重要的原则：每一个测试都应当能被快速地理解。测试名字描述了它检查的行为，断言清楚地表达了期望的结果。开发者在修改代码后，如果某个测试失败，应当能够直接从测试名字和断言中找到问题所在。

另一个原则是，错误信息的测试和正常输出的测试同样重要。`dc` 的很多价值体现在错误报告中，比如带行号的消息和段错误的输出。因此，测试中有大量的断言专门检查错误的内容，确保它们的格式和位置不会在重构中被意外改变。

测试还承担了一个文档的作用。读者可以通过阅读测试来了解某个功能应当如何使用，以及它在边界条件下的行为。例如，`dc sleep 4` 应当失败，这一点在测试中有明确的断言。

总之，`dc` 的测试策略从小到大，从单元到端到端，覆盖了从命令行到解释器的每一层。它的目标是让每一次改动都能被快速验证，也让梦境编程的仪式不会因为实现的偶然错误而失效。
