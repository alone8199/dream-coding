# 12 持续集成中的梦：Actions 如何验证梦

梦境编程的核心在睡眠中完成，但它并不排斥持续集成。相反，持续集成是白天验证梦境脚本的重要手段。本项目的 `.github/workflows/build.yml` 就是一个例子：它把梦境脚本和运行时放在同一条流水线中检查，确保梦境在白天也能被真实地执行。

这条流水线分为两个任务。第一个任务是构建，它在 Ubuntu、macOS 和 Windows 上分别配置、编译、运行单元测试，然后安装 `dc`。Ubuntu 上还会额外构建一个 Debug 版本。Debug 构建不做优化，某些在优化后会被掩盖的问题会在这里暴露。第二个任务是发布，它只在推送版本标签，或者手动触发并填写版本号时运行。

构建任务的后半部分是冒烟测试。冒烟测试会用刚刚安装的 `dc` 执行一组固定的命令：查看版本，运行入口梦境，检查示例脚本的语法，验证示例的输出，并确认运行时错误会以退出码 4 结束。这些检查确保 `dc` 的基本行为没有被破坏，也确保 `dreams/` 目录下的脚本始终是可以运行的。

冒烟测试中有一条值得注意的规则：睡眠时长低于七小时必须失败。这条规则在 CI 中被显式地检查。如果有人不小心改变了下限，流水线会立刻报错。这体现了梦境编程的一个原则：即使是仪式性的规则，也需要被自动化地保护。

持续集成还承担了另一个作用：它记录了每一次构建的历史。当某个平台上的构建失败时，开发者可以在醒来后查看日志，判断问题是否来自梦境脚本，还是来自运行时本身。这种记录让解梦有了更多的依据。

需要注意的是，持续集成验证的是白天的状态，而不是梦境的内容。CI 不会读取你的梦，也不会判断梦是否正确。它只保证代码在真实的环境中能够编译、测试和运行。梦境的价值仍然需要开发者自己去解读。

总之，持续集成是梦境编程与现实之间的桥梁。它让白天的工作有了可靠的验证，也让夜晚的梦境有了可以被检验的基础。两者相互配合，才构成了完整的工作流。
