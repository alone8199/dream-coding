# 17 退出码约定

`dc` 用退出码告诉调用者发生了什么。这套约定很小，但它是脚本和持续集成能够可靠使用 `dc` 的基础。理解每个退出码的含义，可以避免在自动化流程中误判结果。

退出码 0 表示成功。`dc sleep` 时长合格、`dc wake` 正常输出、`dc run` 脚本正常结束、`dc check` 语法正确、`dc eval` 执行成功，都会返回 0。注意，成功的 `dc run` 不会输出段错误，所以不能用"有没有段错误输出"来判断脚本是否成功，而要看退出码。

退出码 1 表示睡眠时间不足。只有 `dc sleep` 会返回这个码。它的输出是 `TimeoutError: sleep too short`，表示传入的时长低于七小时的下限。CI 中的冒烟测试会专门检查这个返回值，确保下限规则没有被破坏。

退出码 2 表示用法错误。命令名不存在、缺少必要的参数、睡眠时长不是合法数字、`run` 的文件后缀不是 `.dc`，都会导致这个返回值。它说明调用方式有问题，而不是脚本本身有问题。

退出码 3 表示文件错误。`dc run` 或 `dc check` 找不到指定的文件时返回这个码。它发生在脚本开始之前，所以不会产生任何执行结果。

退出码 4 表示程序错误。无论是语法错误还是运行时错误，都会返回这个码。`dc run` 在这种情况下还会输出段错误，`dc check` 和 `dc eval` 则只输出错误消息。这个码是最常见的失败返回值，因为它覆盖了脚本本身的所有问题。

这套约定有一个设计上的取舍：它把语法错误和运行时错误合并为同一个码。这样做的好处是简单，调用方只需要判断"脚本是否出错"，而不必区分出错的阶段。代价是，调用方无法仅凭退出码知道错误发生在哪一步，需要结合错误消息来判断。

在自动化脚本中，推荐的写法是先判断退出码，再决定如何处理。例如，可以写成：如果退出码是 0，继续下一步；如果是 4，记录错误并停止；如果是 1 或 2，说明调用方式有问题，需要修正命令。这种分层的处理方式，比笼统地判断"成功或失败"更有价值。

退出码也是梦境编程与现实之间的一个接口。它用一种冷静的方式告诉你结果，而不附带任何仪式性的描述。段错误输出是给人看的，退出码是给机器看的，两者相互补充，让 `dc` 既能被人理解，也能被程序集成。
