# 35 版本与发布流程

版本号让使用者知道他们在使用哪一个版本的 `dc`，发布流程则确保每个版本都是可以被下载和验证的。`dc` 的版本和发布都有明确的约定，理解它们有助于判断某个行为是否来自特定的版本。

版本号分为三个部分，采用语义化版本的基本规则。目前版本号写在两个地方：CMake 配置中的项目版本，以及运行时代码中的 `kVersion` 常量。两处必须保持一致，`dc version` 输出的就是后者。发布新版本时，两处都需要更新，否则输出的版本号会与发布标签不一致。

变更记录写在 `CHANGELOG.md` 中，它遵循 Keep a Changelog 的格式。未发布的改动先记录在 `Unreleased` 小节下，按照新增、修改和修复等类别分组。发布时，把这些内容移到带有版本号和日期的小节中。中英文版本的变更记录应当同步更新。

发布流程由持续集成完成。构建任务会在三个平台上编译并测试 `dc`，并把每个平台安装后的结果打包成压缩文件。发布任务则负责创建 GitHub Release，把这些压缩包附加到 Release 中。发布任务只在两种情况下运行：推送以 `v` 开头的标签，或者手动触发 workflow 并填写版本号。

手动触发是本项目目前推荐的方式。它的好处是，发布的提交和标签都由 Actions 自己创建，不需要从本地推送标签。在 Actions 页面运行 `build` workflow，填写形如 `v0.3.0` 的版本号，流水线会在当前提交上创建标签，并发布对应的 Release。

发布产物是按平台分别打包的 `tar.gz` 压缩文件。压缩包的内容来自 `cmake --install` 的输出目录，其中包含 `bin/dc` 可执行文件。使用者可以下载对应平台的压缩包，解压后直接运行。

版本的历史可以在 Release 页面中查看。每个 Release 都附有自动生成的更新说明，列出了该版本之间的提交。对于需要详细说明的版本，应当在 `CHANGELOG.md` 中补充更完整的描述。

回滚和修复也遵循同样的流程。如果某个版本存在严重问题，应当发布一个新的修复版本，而不是修改已有的标签。这保证了使用者可以信任版本号所代表的内容，也保持了历史的可追溯性。

总之，版本与发布流程的核心是可复现和可验证。版本号告诉使用者他们拥有什么，持续集成确保产物是从已通过测试的代码构建的，变更记录则解释了每一次改动的原因。
