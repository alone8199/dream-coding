# 04 梦境编程的三条原则

梦境编程的流程看起来随意，但它背后有三条明确的原则。这些原则写在 `CONTRIBUTING.md` 中，也是所有参与者都应当遵守的约定。理解它们，比记住每一步的命令更重要。

第一条原则是：不要 debug。

调试是白天开发者最熟悉的动作：看到报错，定位原因，修改代码，再运行一次。梦境编程要求放弃这种动作。当醒来后看到 `Segmentation fault (dream dumped)`，正确的反应是接受它，然后去解读它的含义，而不是立刻打开编辑器去修补。这条原则的目的，是防止开发者把睡眠当成延长的白天，让梦境失去独立的价值。

第二条原则是：不要强行 commit。

提交代码是一个确定性的动作，它把某个状态固定下来，供别人审查和使用。梦境编程认为，这种确定性在睡眠之前是不成熟的。只有在入睡时，或者醒来后仍然记得梦的内容时，才适合提交。强行提交一段在白天写下、在梦里未经验证的代码，会让仓库里充满不可靠的历史。

第三条原则是：不要 deploy。

部署意味着把代码交给真实的环境。梦境编程要求醒来后假装什么都没发生，也就是说，不要把梦里的结果带到现实中去。这条原则不是要求人们对结果视而不见，而是提醒人们，梦境中的运行和真实的运行是两回事。在梦里通过的测试，不代表在现实中也能通过。

这三条原则有一个共同点：它们都在约束开发者的冲动。白天的开发者习惯于立即行动，而梦境编程要求他们克制。这种克制并不是为了懒惰，而是为了给思考留出空间。

在实际的团队协作中，这三条原则也有助于划定边界。当一个 PR 是在梦里写的，审查者应当意识到它的不确定性，并且在醒来后的第二轮审查中再次确认。这样既尊重了梦的价值，也没有放弃对质量的把关。

遵守原则并不容易。很多开发者会在醒来后忍不住修改代码，或者在睡前匆忙提交。但每一次违背原则，都会让梦境编程变成普通的开发方式。坚持这三条原则，才是这项技术与其他开发方式真正的区别。
